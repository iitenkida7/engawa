# 入室券（entry ticket）仕様

[English](./entry-token.md) | 日本語

engawa のオフィスは、「誰を入れるか」の判断を**運用しているコントロールプレーンに委ねる**ことができます。
共通の合言葉を全員に配る代わりに、コントロールプレーンが短命の**入室券**に署名し、ブラウザがそれをリンクで持ってきて、
オフィスが**手元の鍵でローカルに検証**します。

任意機能です。設定しなければ何も変わりません（`ACCESS_PASSWORD` は従来どおり。自己ホストのオフィスはこの仕組みに一切触れません）。

## なぜあるのか

`ACCESS_PASSWORD` は**全員で共有する 1 つの合言葉**です。URL と合言葉を知っていれば誰でも入れ、期限はなく、
セッションからは「その人が誰なのか」が分かりません（アバターの名前は本人が打ち込んだ文字列です）。

自分たちのオフィスを自分たちで立てるならそれで十分です。けれど engawa を**誰かのために**運用する場合は形が合いません。
アカウントはすでに別の場所にあり、人は増えたり抜けたりし、文字起こしや録画は**名前が本物でなければ残す意味がありません**。

そこで、engawa にユーザー・セッション・サインインを教え込む（＝二重の認証基盤を作って同期し続ける）のではなく、
**コントロールプレーンが署名した券を受け取るだけ**にします。

```
①  コントロールプレーン   入室券を発行:  HMAC-SHA256(CONTROL_PLANE_TOKEN, payload)
②  ブラウザ               https://office.example/?t=<入室券> を開く
③  オフィス               手元の鍵で検証し、券に書かれた名前で入室させる
```

性質として明示しておきたいことが 2 つあります。

**問い合わせを発生させない。** ③ はローカルな計算だけです。オフィスがコントロールプレーンに
「この券は有効か」と聞きに行くことはないので、**コントロールプレーンが落ちていても、動いているオフィスには入れます**。
人と部屋の間に新しい障害点を置きません。代償として、**期限前に券を取り消せない**ため、寿命に上限を設けています（後述）。

**名前は券から取る。** このモードでは join メッセージの名前は無視します。名前は署名に含まれるので詐称できず、
**文字起こしや録画が「入力欄に打たれた文字列の記録」ではなく「実際に誰がいたかの記録」になります**。

両者は最初から 1 つの秘密を共有しているので、**HMAC で十分**です（説得すべき第三者がいないので、鍵ペアは要りません）。
[設定レスポンスの署名](./control-plane.ja.md)・[イベント Webhook](./webhook.ja.md) と**同じ方式**なので、覚えることは増えません。

## 設定

| 変数 | 既定 | 説明 |
|---|---|---|
| `ENTRY_MODE` | `password` | `token` で入室券モードになります。それ以外（打ち間違いを含む）はすべて従来のパスワードゲートです。 |
| `CONTROL_PLANE_TOKEN` | 未設定 | **検証鍵**。`ENTRY_MODE=token` のときは必須。コントロールプレーンの認証に使っているものと同じトークンです。 |

`ENTRY_MODE` は[コントロールプレーンのホワイトリスト](./control-plane.ja.md)に入っているので、管理側から切り替えられ、
**次の入室から**効きます（再起動不要。いま入っている人は切断されません）。

`CONTROL_PLANE_TOKEN` は**意図的にホワイトリストに入れていません**。これは秘密そのものであり、
「答えた相手が指定した鍵」で検証しても、何も検証したことになりません。

### 2 つのゲートは排他

`ENTRY_MODE=token` のとき、入室パスワードは**一切参照しません**（環境変数に `ACCESS_PASSWORD` が残っていても何も開きません）。
`GET /api/config` も `passwordRequired: false` を返すので、ブラウザにパスワード画面は出ません。
逆に `ENTRY_MODE` が未設定・`password` のときは、券は要求も参照もされず、join に紛れ込んだ `entryToken` は無視されます。

### 鍵はオフィスごとに

`CONTROL_PLANE_TOKEN` は**オフィス（サーバー）ごとに発行**してください。共有しないこと。
券は「それを署名した鍵を持つすべてのオフィス」で通ります。1 オフィス 1 鍵にしておけば、漏れても券も影響も 1 オフィスに閉じます。

## 券の形式

```
<payload>.<signature>
```

- `payload` — クレーム JSON の `base64url`（**パディングなし**）。
- `signature` — `HMAC-SHA256(CONTROL_PLANE_TOKEN, payload)` の `base64url`。
  ここでの `payload` は、**上の base64url 文字列そのもの**です（デコードした JSON ではありません）。

JSON ではなくエンコード済みの文字列に署名するので、**券が運ぶバイト列と検証するバイト列が一致**します。
「JSON の正規化」という、両側で間違えやすい問題が発生しません。

### クレーム

```json
{
  "userId": "u_8f21c0",
  "name": "石井 剛",
  "exp": 1799884800
}
```

| フィールド | 型 | 意味 |
|---|---|---|
| `userId` | 文字列・1〜128 文字 | コントロールプレーン側の本人 ID。**必須**（券は「誰の券か」が決まっているべきで、持参人払いの切符ではないため）。engawa 側は**保持しません**（接続には接続ごとの ID があり、接続より長く残るものは持ちません＝不変条件 #2）。 |
| `name` | 文字列・空でない | 表示名。そのまま使います（他の名前と同じく 24 文字で切ります）。 |
| `exp` | 数値 | 有効期限。**UNIX 秒**。 |

知らないフィールドは無視するので、コントロールプレーン側が独自の項目を足しても古いオフィスは壊れません。

### 寿命

**想定は 12 時間程度**です。リロード・ノート PC を閉じる・トンネルでの切断のたびにコントロールプレーンへ戻らせない程度には長く、
リンクが漏れても恒久的な鍵にはならない程度には短い、という釣り合いです。

オフィスは**残り 24 時間を超える券を拒否**します（`too-long`）。期限前に取り消せない以上、券の寿命がそのまま影響範囲だからです。
ついでに、`exp` をミリ秒で署名してしまうありがちな間違いもここで落ちます。

### 発行のしかた

```js
// Node.js。secret はそのオフィスの CONTROL_PLANE_TOKEN。
import { createHmac } from 'node:crypto';

function mintEntryTicket(secret, { userId, name }, lifetimeS = 12 * 60 * 60) {
  const claims = { userId, name, exp: Math.floor(Date.now() / 1000) + lifetimeS };
  const payload = Buffer.from(JSON.stringify(claims), 'utf8').toString('base64url');
  const signature = createHmac('sha256', secret).update(payload).digest('base64url');

  return `${payload}.${signature}`;
}

const url = `https://office.example/?t=${mintEntryTicket(secret, user)}`;
```

engawa 側の実装は `engawa/server/src/entry.ts` の `signEntryToken` です。
コントロールプレーンが TypeScript なら、作り直さずそのまま使えます。

## 使われ方

1. コントロールプレーンが `https://office.example/?t=<入室券>` へ送り出します。
2. ブラウザは券を読み取ったら**即座にアドレスバーから消し**（`history.replaceState`）、
   `localStorage` の `engawa-entry-token` に保持します。クエリ文字列は URL の中で最も引用・スクショ・`Referer` 漏れしやすい部分であり、
   ここに入っているのは資格情報だからです。
3. join のたびに（**自動再接続も含めて**）券を提示します。WebSocket の join が本番のゲートで、
   `GET /api/config` は「どの画面を出すか」をブラウザに教えるだけです。
4. **リンクの券は保存済みの券より優先**されます（新しいリンクを送れば必ずそちらが使われます）。
5. サーバーに券を断られたら、ブラウザは券を捨てて「入室リンクが必要です」と表示します。
   再試行する意味はありません（入り直す道は新しいリンクだけです）。

## 拒否される券

入室券モードの join は、券が次のいずれかのとき拒否されます（`auth-error` を返してコード `4001` で切断）。

| | |
|---|---|
| missing | 券が提示されていない |
| malformed | `<payload>.<signature>` の形でない／2048 文字超／クレームが使えない（`userId` なし・`name` なし・`exp` が数値でない） |
| bad-signature | 改竄されている、または別の鍵で署名されている |
| expired | `exp` を過ぎている |
| too-long | 残り寿命が 24 時間を超えている |
| no-key | このオフィスに検証用の `CONTROL_PLANE_TOKEN` が無い |

最後のものは設定ミスですが、**閉じる側に倒します**。「券を要求せよ」と言われたのに検証する鍵が無いオフィスは、
全員を入れるのではなく**全員を断ります**。

ブラウザには「その券では入れなかった」ことだけを伝えます。期限切れなのか偽造なのかはブラウザの関心事ではありません。
理由はサーバーのログにだけ出し、**券と鍵の値は出しません**。

## セキュリティ上の注意

- **HTTPS 必須**（他と同じ）。券は URL に載る資格情報です。
- **鍵はオフィスごと**に発行し、イメージに焼かずに**実行時のシークレット**で渡します（fly なら `fly secrets set`）。
- 券は**短命で、取り消せません**。期限より早く締め出したいときは、そのオフィスの `CONTROL_PLANE_TOKEN` を**ローテーション**します
  （そのオフィス向けの未使用の券がすべて一度に無効になります）。
- 署名の照合は**定数時間比較**。長さが合わない署名も、エラーではなく通常の拒否として扱います。
- **券や鍵の値はログに出しません**（成功時も拒否時も）。
- 券が決めるのは「入れるかどうか」だけで、「何ができるか」ではありません。engawa に参加者の区別はありません。
  ロールや権限が要るなら、それはコントロールプレーン側の関心事です。
