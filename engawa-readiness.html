目標：Gather から全面移行し、社内メインツールとして常時利用＋最大 23 人の全体会議に耐える

コードベース（main 最新）を調査した事実ベース。優先度 P0 必須 / P1 運用品質 / P2 改善。工数 S/M/L。

結論：サーバーと信頼性は 23 人でも持つ。詰まるのは「大人数 SFU の受信ストリーム爆発」

シグナリング負荷（broadcast O(n)・近接計算 O(n²) を 33ms スロットル）、メモリ、再接続/復帰（15 秒 grace）は 23 人で問題なし。

一方で、同一 SFU グループの全員が互いの全ストリームを無条件に pull する設計のため、23 人会議では 1 人あたり最大 ~44〜66 本（他 22 人 × mic+cam(+screen)）を受信し、CPU・帯域が破綻します。これが 23 人 all-hands の唯一にして最大の障壁です。アクティブスピーカー/表示タイルだけに絞る仕組みが未実装。

※ 直近の本番不調（5 人で P2P 切替・音切れ・カメラ自動オフ, #235）も根は同じ「大人数での受信/帯域過多」。540p 化（#236）で緩和しつつ、下記 P0 が本丸。

P0 — 23 人 all-hands を成立させる必須対策

「全員が全員を受信」をやめ、見えている/話している人だけに絞る。ここが通らないと大人数会議は不可。

P0 表示中タイルだけ pull／非表示は受信停止 工数 L

画面に出ていない（focus-hidden・ページ外）ピアの映像は pull を止める。現状はレイヤー画質（f/h）を選ぶだけで本数は減らない。

効果：23 人でも実受信を表示タイル数（例 5〜9）に限定 → 帯域・デコード CPU を 1/3〜1/5 に。

関連：rtc/sfu.ts setPeerTracks/pullTrack、ui/remote-media.ts cameraTileWidth、core/app.ts updateSfuLayers

P0 アクティブスピーカーに音声を絞る 工数 M

23 人全員の音声を常時デコード/ミックスしている。発話中の上位数名＋自分の近傍のみ受信し、無音ピアは止める。

効果：音声デコードの CPU スパイクを解消（音切れの主因のひとつ）。

関連：ui/remote-media.ts remoteAudios / updateSpeaking、rtc/sfu.ts

P0 大人数レイアウト（ページング＋発表モード） 工数 M

タイルの同時表示数に上限を設け、残りはページ送り／名簿に。全体会議向けに「発表者数名＋他は音声/サムネ」の発表モード。上の 2 つと連動して受信本数を決める UI。

関連：ui/remote-media.ts（タイル上限・ページング）、ui/panels.ts

P0 SFU グループサイズの上限／挙動確認 工数 S

会議室ゾーンに 23 人入ると 1 つの SFU グループ（サイズ上限なし）。上限や縮退挙動を明示し、超過時の方針（発表モード強制など）を決める。

関連：server/src/logic.ts computeProximityGroups / SFU_PROMOTE_AT

P0 本番の SFU 安定性・容量の確認（#235） 工数 S

「P2P に切り替えました」は SFU 失敗時のみ。本番で頻発＝SFU が不安定。Cloudflare Realtime の認証/容量/レート上限、フォールバックの粘り（1 回失敗で mesh に落とさない）を点検。

関連：server/src/sfu.ts isSfuEnabled、core/app.ts onSfuFailed、rtc/sfu-logic.ts

P1 — 常時メインツール化に必要な運用品質

毎日使う／全体会議を回すのに実務上ほぼ必須の機能群。

P1 参加者名簿（ロスター） 工数 M

全参加者を一覧（名前・マイク/カメラ・離席）。現状はタイルのみで、画面外の人が把握できない。23 人の点呼・状況把握に必須。

※ 以前ロスターを撤去（#219）したが、大人数運用では「俯瞰一覧」として再導入価値が高い。

P1 全体会議向けモデレーション 工数 M〜L

  • 全員ミュート／特定参加者の強制ミュート
  • 強制退出（kick）・入室ロック（遅参停止）
  • 画面共有の同時数制限
  • ロール（発表者／聴講者）

※ サーバーがステートレス（不変条件 #2）なので、権限は一時メモリ＋再起動リセットの範囲で設計。

P1 観測性（ログ／メトリクス） 工数 M

SFU API 失敗率・再接続率・近接再計算のレイテンシ・メディアトークン残量などを計測。/api/health を接続数以外にも拡張。障害時に原因を切り分けられる状態にする。

P1 エラーのユーザー通知 工数 S

TURN 取得失敗・WebRTC 接続失敗・group-update 不達などを UI で明示（現状は暗黙失敗が多い）。SFU→mesh フォールバックのトーストは既にあり。

P1 入室前デバイスチェック 工数 S〜M

参加前にマイク/カメラの選択・プレビュー・権限確認。会議開始時の「音が出ない」事故を防ぐ。

P1 実機負荷テスト 工数 M

実際に 23 人（＝SFU）でCPU/帯域、Cloudflare TURN/SFU の API 回数・レイテンシ・課金を実測。P0 の効果検証もここで。デバッグコンソール（🐛）の qualityLimitationReason（cpu/bandwidth）を指標に。

P2 — あると運用が快適

P2 運用の細かな機能 工数 S 各

  • 一定無操作で自動「離席」
  • 録画インジケータ（誰が録画中か全体表示）
  • 入退室チャイム／呼び出し通知の整理
  • 録画は大人数では SFU 前提（全 mesh 録画は非現実的）

設計上の制約（計画に織り込む）

制約内容23人運用での方針
単一インスタンスクライアントはプロセス内メモリ管理。水平スケール不可（1 インスタンス必須）1 社なら許容。再起動は 15 秒 grace 内で復帰。無停止更新は別途検討
Cloudflare 依存TURN/SFU は Cloudflare Realtime。障害時は STUN フォールバック（＝mesh 化）本番の認証/容量/レートを確認（#235）。SLA を把握
ブラウザのみデスクトップ/モバイル専用クライアントなし対応ブラウザを社内標準化（Chrome 系推奨）
ステートレス（不変 #2）グループ/ラッチ/権限は一時メモリ権限・モデレーションもメモリ前提で設計（再起動でリセット可）

進め方の提案

フェーズ1（大人数を成立させる）：P0 の受信絞り込み（表示タイル pull＋アクティブスピーカー音声）＋発表モード＋#235 の本番 SFU 確認。これで 23 人 all-hands が「動く」状態に。

フェーズ2（毎日使える品質）：名簿・モデレーション・観測性・エラー通知・デバイスチェック。運用で回せる状態に。

フェーズ3（磨き込み）：自動離席・録画表示・負荷テストで本番定着。

各項目は GitHub Issue 化して順に着手できます。まずフェーズ1のどれから入るか決めましょう（おすすめ：#235 の本番 SFU 確認 → 表示タイルのみ pull）。
